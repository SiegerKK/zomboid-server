# Story Director — большой скан локации (эксперимент)

Разработка поверх PR #8. Только `story_test`, без восстановления мира и без изменения `road_home`.

## Команды

```bash
sudo pz story scan-player story_test GAME_LOGIN --side 101 --yes
sudo pz story scan-status story_test
sudo pz story scan-report story_test --output /var/tmp/quest-location-scan.json
```

`--side 101` означает 101×101 клетку: от X−50 до X+50 и Y−50 до Y+50, пять уровней по Z (всего 51 005 кандидатов). Это **квадрат**, не евклидов круг радиусом 50 метров. Для маленькой области доступны `--side 25` (старое поведение) и `--side 51`. Центр фиксируется в момент получения сервером запроса. Работа только с подключённым персонажем; принудительная загрузка чанков запрещена.

В расширенных отчётах добавлены записи `kind=square` с полем `loaded` для каждой обследованной клетки, пока не достигнут лимит отчёта. `loaded=false` = результат `getGridSquare=nil`, **не доказательство пустоты**: клетка могла быть незагруженной или отсутствовать (например, воздух). `loaded=true` не означает, что объект полностью пригоден для взаимодействия; нужны актуальные селекторы и клиентская проверка.

Остальные записи прежние: `object`, `container`, `container_item`, `ground_item`, `static_object`. Отчёт не содержит полного графа комнат, точной принадлежности здания, всех блокирующих путей, автомобилей, игроковых инвентарей и живых заражённых. Для квеста врагов нужно спроектировать и отдельно проверить новый адаптер, он **не реализован**.

## Важные ограничения

- Бюджет обхода прежний: до 20 завершённых клеток / 200 шагов работы за тик. Новые размеры 51/101 значительно тяжелее; перед игровым тестом выполнить Lua/Python harness в pinned Build 42.21.0 и измерить нагрузку на VPS.
- Лимит данных в Lua 24 MiB / 140 000 записей; Python принимает не больше 32 MiB / 140 005 строк. При лимите вывод `partial/truncated`, а не «полный» результат.
- Результат — инкрементальный снимок; во время обхода состояние мира может измениться. Не использовать старые object_index без повторного подтверждения непосредственно перед сценой.
- Никогда не публиковать полный снимок в Git: он может включать предметы и координаты чужих баз. Выгружать `--output` только вне репозитория; файл создаётся с 0600.
- Не менять мир от одного сканирования. Никакой автоматической загрузки клеток, сброса/рестарта VPS, RCON eval, новых портов.
- Большое количество `loaded=false` = неполные данные, даже при статусе `complete` (он означает лишь, что очередь клеток пройдена без ошибок). Для полноценного здания можно сделать несколько сканов из разных точек при обычной клиентской загрузке области и объединить приватно, не объявляя несовпадающие временные снимки атомарными.
- Новый runtime требует **согласованного** короткого обслуживания при RCON players=0. До установки новой версии в активный мир команда `--side 101` не работает.

## Приёмка

1. Lua 5.1 и exact-game Kahlua harness; Python тесты; сохранение v1 25×25×5; ответ на v2 51×51×5 и 101×101×5.
2. В существующем `story_test` после разрешённого развёртывания: запрос 101×101×5, проверка ID, meta/footer, `square` coverage, errors/truncated и фактического времени/нагрузки.
3. Экспорт JSON, проверка mode 0600, консистентности счётчиков и отсутствия персональных данных в Git. Не считать partial полноценным сканом; при необходимости уменьшить область или сделать несколько маленьких запросов.
4. Заполнить PASS/FAIL/BLOCKED, оставить `story_test` работающим без восстановления.

Для первого квеста: получить скан и передать JSON в ChatGPT, после чего выбрать конкретные шкафы, точки с заметками, маршруты и разрешённые spawn-позиции. Сами сцены должны храниться как проверенные JSON-манифесты в Git, а не как произвольные исполняемые Lua-скрипты.
