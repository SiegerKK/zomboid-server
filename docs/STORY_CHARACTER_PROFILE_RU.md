# Персонаж: аудит и серверное восстановление снаряжения

Версия кода `radio-inv17`, Build 42.21.0. **Новый механизм требует игровой приёмки.**
История ошибок: [отчёт об инциденте](STORY_CHARACTER_INCIDENT_RU.md).
Старый `character apply` **заблокирован** в CLI, серверном и клиентском Lua.
Он не должен снова менять локальный инвентарь, навыки или раны.

## Команды

```bash
sudo pz story character audit story_test LOGIN --profile joel-arrival-v1 --yes
sudo pz story character status story_test
# После аудита и безопасного архивирования предыдущего протокола:
sudo pz story character repair story_test LOGIN --profile joel-arrival-v1 --item Base.Revolver
sudo pz story character repair story_test LOGIN --profile joel-arrival-v1 --item Base.Revolver --yes
# Весь комплект — только после игровой проверки первого оружия:
sudo pz story character repair story_test LOGIN --profile joel-arrival-v1 --yes
```

Без `--yes` repair является preview. `Base.308Bullets` с цифрой в начале имени
поддерживается. Сервер разрешает только типы из фиксированного профиля,
текущий story_test и точный подключённый логин. Клиент не может начать выдачу сам.
Предыдущий запрос, включая ошибочный/частичный, автоматически не заменяется.
После аудита оператор сохраняет protocol/receipt/manifest в приватном каталоге;
архивирование протокола не означает rollback мира или повторение мутации.

## Владение и доставка предметов

1. Клиент отдаёт ограниченный read-only снимок: ID, FullType, container path, condition.
   Сервер одновременно снимает свой снимок. До этого никакие предметы не удаляются.
2. Сервер сравнивает конкретные ID. Совпавшие серверные предметы сохраняются.
   Создаются только недостающие до минимального количества в профиле экземпляры,
   с серверными ID и modData tag `SiegerInventoryRepair`. Легитимные излишки не удаляются.
3. Только клиентские профильные предметы, ID которых отсутствуют на сервере,
   становятся кандидатами на cleanup. ID collision, изменившийся контейнер или
   ghost-сумка с сохраняемыми вещами приводят к отказу до удаления.
4. Клиент убирает только согласованные ghosts по ID/type/path. При изменении снимка
   или неопределённой попытке он отказывает. Серверные предметы клиент не создаёт,
   не копирует через `instanceItem` и не назначает им ID вручную.
5. Сервер прикрепляет новые экземпляры к настоящему inventory и вызывает
   `sendAddItemToContainer` на сервере. В настоящем B42 JAR этот путь адресует
   владельца через `ItemContainer.getCharacter()` и сериализует тот же экземпляр
   штатным AddInventoryItemToContainer packet. Вложенные контейнеры имеют рекурсивного owner.
   Для уже известного предмета с разным condition используется серверный `syncItemFields`.
6. Клиент ждёт штатных пакетов до 20 секунд и проверяет ID/type/path/condition.
   Сервер повторно проверяет свои экземпляры. Только тогда receipt становится
   `complete / server_inventory_verified`.

Новые предметы выдаются в **основной инвентарь**. Нет автоматического заполнения
или экипировки нового рюкзака: это проверяется обычными игровыми действиями.
Существующие канонические вложенные предметы остаются в своих контейнерах;
неподтверждённая цепочка родительских контейнеров не заменяется догадкой.

`server_inventory_verified` означает совпадение identity, а не успешную ручную
экипировку, выстрел или сохранение после relog. Эти этапы принимает владелец в игре.

## Сохранность и пределы

- Repair **не** сбрасывает навыки, здоровье, голод, раны, одежду, прогресс или посторонние вещи.
- Цель — минимум профильного снаряжения. Ремонт не реставрирует расходованные патроны
  при каждом подключении: требуется новый явный root-запрос. Уже существующие вещи
  не чинятся и не заполняются заново без отдельной операции.
- Для клиента/сервера предел 512 предметов и глубина 4. Больший снимок отказывает.
- Перед доставкой сохраняется серверный ledger с ожидаемыми ID; перед первой записью
  отмечается `server_mutation_started`. Ошибка доставки даёт явное uncertain/partial,
  ничего автоматически не восстанавливается и не повторяется.
- Guard и отдельный ledger для каждого request ID не позволяют переотправить запрос
  после restart или при историческом replay. Новый ID не является разрешением
  вслепую повторить нерасследованную частичную операцию.
- Клиентский cleanup marker ставится **до** первого удаления, повторная CLEAN с тем же
  ID не удаляет заново. Полноценной атомарной транзакции игровых объектов нет.
- Снимки до/после и manifest находятся только в VPS-only `data/Lua/`; exports хранятся
  под root-only manager. Не публиковать ID/инвентари/логины/координаты в GitHub.
- Read-only audit также сообщает wound timers и bandaged flags: `scratched()==false`
  у перевязанной части тела само по себе не означает, что рана вылечена.

## Ping limit

По просьбе владельца `PingLimit=0`: отключён только disconnect за высокий пинг,
а не измерение пинга, сетевые таймауты или остальные проверки.
Это соответствует `PingManager.doKickWhileLoading`: kick возможен только при limit>0.
`PING_LIMIT=0` разрешён в per-world rules; шаблон tlou-coop задаёт его для новых миров.
Для существующего story_test сохранён отдельный server-rules.env с этой настройкой.
`DoLuaChecksum`, `AntiCheatPermission`, `AntiCheatXP` остаются включёнными.

## Обязательная игровая приёмка

Для обычного игрока: одно оружие → ручные equip/unequip → корректные reload/unload →
перенос main↔рюкзак → сверка серверных ID → save/relog без дубликатов.
Затем повторить для комплекта, подтвердить второго клиента и restart replay.
Нельзя объявлять PASS только по CLI, поднимать роль игрока или отключать античит.
