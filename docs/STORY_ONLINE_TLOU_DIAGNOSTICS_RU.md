# Онлайн-диагностика Project Zomboid / TLOU — PR #27

**Статус: Draft. Runtime `8dd58f6` установлен на Build 42.21 / story_test.**
Проверка CLI выявила описанную ниже ошибку путей. Исправленные команды
требуют повторной серверной проверки и совместимого клиентского пакета
SiegerRadio; multiplayer-приёмка остаётся отдельным этапом. Диагностика
не изменяет зомби или игровые предметы.

## Полезные команды

```bash
# Список реально подключённых игроков, координаты, ID их машин:
sudo pz story ops players story_test
sudo pz story ops players story_test --yes
sudo pz story ops result story_test

# Локальные угрозы возле онлайн-игрока: зомби, машины, другие игроки,
# ближайший зомби, количество фактически загруженных клеток.
sudo pz story ops nearby story_test --player admin --radius 10
sudo pz story ops nearby story_test --player admin --radius 10 --yes
sudo pz story ops result story_test

# Зарегистрированные TLOU/Zomboid Forge типы, веса и SandboxVars:
sudo pz story tlou registry story_test --yes
sudo pz story tlou result story_test

# ПОЛНЫЙ однократный подсчёт всех загруженных сервером зомби:
sudo pz story tlou census story_test
sudo pz story tlou census story_test --yes
sudo pz story tlou result story_test

# Отдельная сводка по Docker CPU/RAM, не по одному моду:
sudo pz story profile story_test --samples 12 --interval 5
```

Без `--yes` команды создания отчёта показывают **только preview**,
не отправляя запрос серверу. `result` не создаёт и не повторяет операцию.

## Что именно показывает полный TLOU census

В отличие от выборки, `census` делает один последовательный проход по
**каждой позиции списка** `getCell():getZombieList()`. Никакого ограничения
в 512 объектов, пропусков каждого N-го, паузы на 16 элементов за тик
или искусственного предела популяции.

Отчёт содержит:

- Общее количество записей в загруженном списке, сколько объектов реально
  присутствуют и сколько ячеек списка пустые.
- Реальную классификацию `TLOU_Runner`, `TLOU_Stalker`,
  `TLOU_Clicker`, `TLOU_Bloater`, `other`, `unknown`.
- Для каждого типа: количество, среднее здоровье (и размер выборки
  здоровья), сколько движется и сколько имеет цель; рядом размер выборки,
  в которой соответствующий API действительно отработал.
- Ошибки определения типа, неинициализированные outfit ID, измеренное
  время выполнения при доступном `getTimestampMs`.
- Текущий реестр Zomboid Forge: веса типов, отдельные настраиваемые
  свойства (если предоставлены), количество `onTick`-обработчиков и
  выбранные SandboxVars мода TLOU.

**Разделены два показателя:** вес появления в Forge — настройка, а
количество реально загруженных экземпляров — наблюдение, которое
зависит от мира, убийств и текущей подгрузки. Это не одно и то же.

## Что означает «полный»

Сканируются **все загруженные зомби** в текущем серверном
`IsoCell` — без отбрасывания объектов вдали от администратора.
Зомби из выгруженных регионов/чанков не загружаются искусственно:
полная перепись всех сохранённых на диске инфицированных потребовала
бы другого, более тяжёлого офлайн-аудита.

Сам скан не вешает новых обработчиков на зомби и не собирает постоянную
статистику. В простое проверяется только приватный файл запроса
раз в 180 тиков. После `census` данные подсчитываются за **один
серверный тик**; стоимость по времени O(N), по дополнительной памяти
O(1) относительно числа зомби. На очень большой популяции **один тик
может оказаться длиннее обычного** — это честная цена полного быстрого
прохода. Метрика `elapsed_ms` появляется, только если доступен игровой
таймер.

Отдельная мера производительности и безопасности: `ZomboidForge.GetZType`
может выделять память под кеш каждого объекта и менять одежду
неинициализированного зомби. Диагностика **вообще не вызывает его**.
Вместо этого используется уже готовый `NonPersistentZData[zombie].ZType`.
Все экземпляры без кешированного типа учитываются в `unknown`, а не
отбрасываются из общего подсчёта. Так мы не создаём кеши и не меняем
объекты ради отчёта.

## Совместимость и операционные границы

- Все запросы исходят от root-only CLI через локальные Lua-файлы мира;
  клиентские запросы и Lua eval отсутствуют.
- `story_test` обязателен, `road_home` не затрагивается.
- Серверный код доступен через `compose.story.yaml` в обычной конфигурации
  и через чекcум-согласованный `SiegerRadio/42/media/lua/server` в
  радио-конфигурации с `compose.radio.yaml`. Дубли проверяются генератором.
- `registry` вообще не обходит коллекцию зомби. `census` выполняется
  только после отдельного явного запроса.
- Автотесты проверяют пустую нагрузку в простое, скан всех **1300**
  тестовых зомби без отсечения, распознавание типов, отказ на неверном
  мире, защиту от повторных запросов и согласование итоговых чисел.
  Эти тесты **не** доказывают работу с реальным TLOU в Build 42.21.

## Исправление проверки установки на VPS

При фактической установке `8dd58f6` CLI `ops` и `tlou` ошибочно требовали
только старый vanilla Lua bind mount, хотя файлы уже были загружены из
SiegerRadio. Общая проверка `assert_module_ready` принимает оба варианта:
точный vanilla mount либо точные mounts SiegerRadio и приватного bundle
**текущего мира**, с побайтовым совпадением packaged Lua с reviewed runtime.
Чужие data/bundle/code paths, отсутствующий или устаревший handler отклоняются.
Дублирующие vanilla mounts и отключение LuaChecksum не требуются.

Регрессия: `python3 tests/test_story_module_mounts.py` проверяет оба способа
установки, другой активный мир, подменённые пути и устаревший packaged Lua.

Первая живая перепись обработала 7/7 зомби, но показала `framework=unavailable`
и 7 `unknown`: мод возвращает локальную таблицу, а Kahlua не предоставляет
обычный `package.loaded`. Исправленный доступ сначала подтверждает файл
`ZomboidForge_module.lua` через `getLoadedLuaCount/getLoadedLua`, затем получает
**уже сохранённый** результат `require` из Java `LuaManager.loadedReturn`.
В одинаковых клиентском/серверном JAR проверено, что `RunLuaInternal` возвращает
этот кеш до компиляции/исполнения модуля. Если файл не загружен, `require`
не вызывается. Диагностика по-прежнему не вызывает `GetZType` и не создаёт
кеши отдельных зомби. Lua-регрессия проверяет отсутствие global/package.loaded,
повторное использование результата и отказ инициализировать незагруженный модуль.

При пустом сервере `PAUSE_EMPTY=true` останавливает OnTick. Запрос остаётся
`pending` до входа игрока; отключать паузу или считать это успешным ACK нельзя.
