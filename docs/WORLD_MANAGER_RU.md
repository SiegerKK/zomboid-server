# Один репозиторий — единый Bash-менеджер миров Project Zomboid

**Статус:** код менеджера и офлайн-тесты добавлены в Pull Request #1 и проверены с поддельным Docker CLI. **На реальном VPS менеджер пока не устанавливался**. Не менять текущие данные и модпак до проверки Codex.

Источники истины: `compose.yaml`, `config/server.env`, `config/mods*.env`, `pz`, `tests/smoke.sh`. Отдельный ZIP/Python-проект больше не нужен. SaaS остаётся независимым Docker Compose в подпапке `saas/`.

## Доступные команды

```bash
sudo pz start                 # предложит пронумерованный список миров
sudo pz start original        # запуск названного мира в фоне
sudo pz stop                  # сохранение + штатная остановка с подтверждением
sudo pz save                  # холодный архив текущего мира, затем перезапуск
sudo pz save-live             # RCON save, без копии и остановки
sudo pz load                  # выбор резервной копии, восстановление в НОВЫЙ слот
sudo pz create winter tlou    # новый мир с профилем mods.env
sudo pz create fresh vanilla  # новый пустой ванильный мир
sudo pz create test mp-test   # альтернативный модпак для тестов
sudo pz list
sudo pz status
sudo pz logs
```

При `start` без аргумента предлагается выбор **по номеру**; при запуске без терминала нужно передать имя мира. `load` — восстановление backup, а загрузка существующего мира делается через `start`. Для фонового запуска используется `docker compose up -d`. `PAUSE_EMPTY=true` при отсутствии игроков приостанавливает игровое время, но НЕ освобождает RAM; `stop` останавливает контейнер.

## Раздельные миры

```text
/opt/zomboid-server/
  compose.yaml         # один Compose / один image / одни игровые порты
  pz                   # один Bash-менеджер
  config/mods*.env     # профили модов из GitHub
  tests/smoke.sh       # офлайн-проверка

/srv/zomboid/
  worlds/
    original/{data,profile}
    winter/{data,profile}
    test/{data,profile}
  manager/active-world
  backups/worlds/<world>/world-DATE-PID.tar.gz
  workshop/            # общий кеш Steam Workshop, не общие сохранения
  data/                # прежний каталог, НЕ удалять при миграции
```

**Каждый каталог `data` содержит весь `/root/Zomboid`, включая Saves, db, Server, sandbox.** Имя сервера внутри мира `SERVER_NAME=SiegerZomboid` сохраняется постоянным, чтобы загрузчик не создавал новый пустой мир при переключении. Профиль модов (`vanilla`, `tlou`, `mp-test`) сохраняется в `profile` и включён в backup. Workshop-кеш общий, но активируемые Mod IDs раздельны.

Сервис может работать **только с одним миром одновременно** на UDP 16261/16262. `pz start` не переключает каталог сохранений, пока контейнер запущен.

## Установка на существующем VPS (делает Codex)

1. Убедиться, что `/opt/zomboid-server` — актуальный root-owned checkout той же ветки GitHub, что содержит `pz` и Compose-поддержку `PZ_WORLD_DATA_DIR`. Проверить отсутствие незакоммиченных изменений и отслеживать фиксированный commit. Не редактировать `.env` в GitHub.
2. Проверить отдельно **офлайн**, без работающего Docker: `sudo bash tests/smoke.sh`; `bash -n pz`; `docker compose config --quiet` с секретами на VPS.
3. Создать команду `pz` через **символьную ссылку**, чтобы код оставался в одном репозитории и всегда был в одной версии с Compose:

   ```bash
   sudo chmod 755 /opt/zomboid-server/pz
   sudo ln -sfn /opt/zomboid-server/pz /usr/local/sbin/pz
   sudo pz --help
   ```

   Проверь, что весь checkout и путь к скрипту не доступны на запись обычным пользователям: `sudo pz` эквивалентен root. Не добавлять kyrylo/ihor в Docker group для управления.

4. Для **существующего** мира сначала запросить окно обслуживания (игроков нет), выполнить RCON save и остановить текущий Compose без `down -v`; выполнить старый `scripts/backup.sh` для каталога `/srv/zomboid/data`; проверить SHA256 и распаковку. Только затем импортировать в отдельный слот, НЕ перемещая и НЕ удаляя исходные файлы:

   ```bash
   # profile определяется по ФАКТИЧЕСКИ включённым Workshop/Mod ID текущего мира.
   sudo pz import-legacy original tlou
   sudo pz start original
   ```

   Здесь `tlou` — лишь **пример**, не универсальная истина. Если текущий мир использует альтернативный TLOU_MP, выбрать `mp-test`, а если нет модов — `vanilla`. Если список Mods/Workshop не совпадает с профилями — остановиться и добавить правильный профиль до импорта.

5. Проверить `pz status`, реальные Mounts контейнера, игровой лог и вход клиента; затем сценарий world A -> stop -> world B -> stop -> world A. Убедиться, что изменения не пересекают миры.
6. Проверить `pz save --yes`: RCON save, корректный stop, SHA-256, перезапуск; `pz load`: извлечение **в новый слот** без модификации оригинала; полная проверка игровых данных и входа. Внешние зашифрованные бэкапы на отдельное хранилище по-прежнему нужны.

## Предохранители

- Общий `flock` на `/run/lock/pz-operation.lock` для операций менеджера и старого backup-скрипта. Команда `logs` снимает блокировку, чтобы `stop` оставался доступен.
- `stop` и холодный `save` предупреждают об отключении игроков и требуют подтверждения; для явного noninteractive stop используется `--yes`.
- Не удалять контейнерные volumes через `down -v`, не изменять live-data во время работы.
- `load` принимает только SHA-256-проверенные архивы менеджера и создаёт **новый** слот; архив из предыдущего legacy-скрипта имеет другой формат и не должен открываться таким способом.
- Не обновлять игру или моды посреди сессии. Snapshot мира без точного списка модов, сохранённого Git commit и версии игры может оказаться несовместим при восстановлении.
- Прямые `docker compose up` из каталога проекта обходят выбор слота и могут подключить прежнюю legacy-папку. После установки менеджера для игры пользоваться только `sudo pz`. SaaS стек управляется независимо.

## Ограничения текущего теста

Офлайн-тесты проверяют маршрутизацию томов, переключение, RCON-вызовы (mock), snapshot с SHA, восстановление и защиту от перезаписи. Они **не доказывают** корректность сохранения в реальном Build 42 или успешную MP-синхронизацию — Codex должен проверить это на VPS перед приёмкой.
