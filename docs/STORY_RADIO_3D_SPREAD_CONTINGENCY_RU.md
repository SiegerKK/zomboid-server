# SiegerRadio PR #24 — подтверждённый дефект 3D-панорамы и стерео-эксперимент

## Наблюдение и измерение видео

Владелец прислал 15,7-секундный ролик из салона автомобиля: при
повороте головы/камеры музыкальное радио резко переходит из одного уха
в другое, а при развороте назад становится едва слышным.
На стереодорожке всей записи (24 кГц анализ, окна 0,75 сек)
локально наблюдаются дисбаланс L/R до ~20 дБ и провалы суммарного
записанного уровня на ~13–15 дБ. Это **общий игровой микс**, не
изолированный сигнал радио. Выводы о точной роли DSP/окклюзии
требуют A/B с фиксированным фрагментом песни и положения камеры.
Ролик не доказывает, что установлен именно head PR #24.

## Причина, которую способен исправить наш мод

Сейчас все 41 музыкальных WAV в `story/radio/catalog.json` —
**mono PCM 22050 Hz 16-bit**. Позиционный `FMOD_3D` размещает
одноканальную музыку как **одну акустическую точку**, что даёт
выраженное разделение L/R при близком слушателе с Viewpoint.
Недавнее увеличение min/max с 1/12 до 4/12 уменьшает затухание
от расстояния, но не исправляет резкое панорамирование по углу.

Официальный FMOD Core `ChannelControl::set3DSpread` распределяет
по пространству **каналы многоканального звука**. Для настоящего
stereo при 0° обе составляющие в одной точке, 90° даёт ±45°,
120° — ±60°. Spread для текущего mono не создаст потерянных
независимых каналов. Поэтому прежнее утверждение о достаточности
моно-WAV + Spread было слишком оптимистичным.

Оригинальные записи могут содержать полноценную L/R пару.
Восстановить стерео можно только из **исходного** `radiomusic.zip`,
а не путём копирования текущего mono в два канала.

FMOD API:
https://www.fmod.com/docs/2.04/api/core-api-channelcontrol.html
Старый PZ JNI (не доказательство Build 42.21):
https://zomboid-javadoc.com/41.65/fmod/javafmodJNI.html

## Подготовленный код (пока НЕ включён в текущем клиентском пакете)

1. Клиентский `SiegerRadioBridge.java` читает ограниченный заголовок
   локального WAV (без загрузки всего файла) и разрешает только
   mono/stereo PCM16 22050 Hz. Дополнительный JNI
   `FMOD_Channel_Set3DSpread(long,float) -> int` находится через
   optional reflection на **точном** клиентском Build 42.21.
2. Если WAV **действительно stereo** и исходный источник стационарный
   либо автомобильный, по умолчанию запрашивается Spread **120°**;
   `FMOD_3D` остаётся включён, канал **один**, координаты радио
   сохраняются. Никакого `FMOD_2D`, `set3DLevel<1`, новой копии
   песни, глобальных FMOD listener-патчей или фонового PCM нет.
3. Если WAV mono, Spread **не вызывается** — используется прежняя
   физическая FMOD_3D точка. Если native метод отсутствует/вернул
   ошибку, проигрывание остаётся в исходном 3D, режим диагностики
   отмечает `stereo_3d_spread_unavailable/failed`: тишину и ложный
   успех не подделывать.
4. Для приёмки можно менять Spread текущего stereo-канала без
   повторного `FMOD_System_CreateSound`, seek или звукового дубликата
   через локальный Lua вызов:
   `siegradioBridgeSetSpread(0|60|90|120|150|180)`.
   Состояние: `siegradioBridgeSpatialStatus()`.
   Некорректные значения, NaN и другие команды отклоняются.
5. FMOD stream+seek запускается только с включённым приёмником,
   дальность обнаружения 12 клеток, near/far остаётся 4/12.
   Обновление Java или клиентского ZIP требует повторного одобрения
   изменённого JAR через ZombieBuddy.

**Важно:** этот код подготовлен и проходит Lua/Java mocks, но
текущие **41 mono-WAV и их SHA-256 не изменены**, поэтому улучшение
по ролику ещё нельзя считать работающим в игре.

## Безопасная подготовка одного реального стереотрека

Нужен **оригинальный radiomusic.zip владельца** с SHA из
`story/radio/owner-tracklist.json`. Скрипт проверит хеш самого ZIP,
каждый SHA исходного трека, реальный 2-канальный исходный звук,
длительность, размер и формат итогового WAV.

Сначала только dry-run, затем создать **НОВУЮ** тестовую папку:

```bash
python3 scripts/radio_stereo_prepare.py \
  --archive /path/radiomusic.zip --track north_track_38 \
  --output /path/to/new-stereo-test

python3 scripts/radio_stereo_prepare.py \
  --archive /path/radiomusic.zip --track north_track_38 \
  --output /path/to/new-stereo-test --yes
```

На выходе будут `pcm/north_track_38.wav`,
`catalog.candidate.json`, `review.json` и
`generated/` (синхронные будущие Lua-регистры/handshake).
**Ни одна** текущая сцена/песня/мод/JAR не заменяется автоматически.
После обзора кандидата тестовая сборка должна применяться только
в изолированном checkout с источниками всех остальных WAV, новым
SHA каталога, новой клиентской версией и одобренным Java JAR.
Пока исходный архив недоступен в текущем сеансе, реальное stereo
собрать и проверить на клиенте невозможно.

Если A/B на ОДНОМ стереотреке устраняет дисбаланс, только тогда
перегенерировать 41 трек через `--all` в отдельную новую папку,
сверить SHA, длительности и размеры, выполнить pack verify, и
распространять совпадающие полные клиентские пакеты.
Два канала PCM займут почти вдвое больше дискового объёма
(~400 -> ~800 МиБ для текущей длины музыки), но **stream** остаётся
один и FMOD читает с диска небольшими блоками при прослушивании.
Точной стоимости CPU/RAM без игрового профайлера не утверждаем.

## Проверка после подтверждения физического 3D-проигрывания

При одинаковом расстоянии 1–3 клетки от радио выполнить
0°/90°/180°/270° в машине с Viewpoint и без него,
сравнивая варианты Spread **0°, 60°, 90°, 120°**.
Затем повторить на 5 и 10 клетках, проверить закрытую дверь,
питание, смену волны 101.2, выход/возврат и двухклиентный эфир.
Если именно `CUE/test_tone` ведёт себя иначе, помнить, что он
использует отдельный `FMODSoundEmitter`, а не Java stream.

Оценивать: отсутствие почти полной тишины позади, сохранение
локализации и плавного L/R перемещения, отсутствие звука после
12 клеток, отсутствие двойных FMOD-каналов, совместимость
общей громкости и 3D-затухания, потребление RAM/FPS.
Проверить реальную `FMOD_Channel_GetAudibility` (если JNI предоставляет)
и системную конфигурацию наушники/stereo/surround перед любой
глобальной коррекцией `listener`.

Даже если Spread работает, Viewpoint может выставлять listener
ориентацию/выходные каналы не так, как ожидается. Тогда вносятся
исправления после отдельной диагностики; **нельзя** ради музыки
менять глобальный FMOD listener и звук остальных игр/модов.

**Статус:** код и тестовый staging находятся только в PR #24,
без развёртывания на VPS, без мержа в main и без изменений save.
Реальный игровой A/B и доступ к исходному архиву — обязательны.
