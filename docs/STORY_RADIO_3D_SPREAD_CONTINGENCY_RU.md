# NORTHBOUND / SiegerRadio: резервный план коррекции 3D-звука позади игрока

**Статус:** исследование и план на случай подтверждения дефекта владельцем.
Этот документ не активирует новый аудиорежим, не меняет музыку, JAR, сервер,
Viewpoint, настройки игроков и мир. Любой новый аудиопрофиль — отдельное
экспериментальное изменение в PR #24 после фактического A/B.

## Задача

В Project Viewpoint музыка из физического стационарного/автомобильного
радио становится почти неслышимой при повороте персонажа/камеры спиной,
хотя координаты источника и слушателя не изменились. Цель: сохранить
**FMOD_3D**, одну физическую позицию устройства, пространственную
локализацию, дальность слышимости в 12 клеток и музыкальный stream+seek
**без фонового воспроизведения**, но не допускать почти полного исчезновения
музыки вблизи только из-за разворота.

Это может быть проблема listener orientation / конфигурации выходных
динамиков, 3D-панорамы или обычного приглушения/окклюзии мира PZ.
Один только факт «тихо сзади» не доказывает необходимость стерео WAV.

## Существенное уточнение: FMOD Spread и MONO

Старое FMOD Core API прямо описывает, что mono-источник тоже может
разделяться внутри пространственного panner как стерео-сигнал
с сохранением суммарной мощности. Поэтому **не конвертировать сразу все
41 файла** из mono PCM в stereo PCM. Сперва проверить 3D Spread
на нынешнем PCM и точной версии FMOD в B42.21. Степень раздвижения
динамиков зависит от output speaker mode и реализации FMOD.
По FMOD Core spread=0 означает одну точку, 90 — пару каналов ±45°,
180 — ±90°, 360 может фактически перекинуть звук в противоположную
сторону и **не должен** быть значением по умолчанию.

Документация:
https://www.fmod.com/docs/2.04/api/core-api-channelcontrol.html
https://documentation.help/fmod-studio-api/FMOD_ChannelGroup_Set3DSpread.html

У старого PZ javafmodJNI (41.65) уже был точный метод
`FMOD_Channel_Set3DSpread(long,float) -> int`:
https://zomboid-javadoc.com/41.65/fmod/javafmodJNI.html
Но эта документация **не подтверждает** ABI на 42.21. Метод должен
обнаруживаться reflection в фактически установленном клиентском JAR.

## Сначала определить вид неисправности (ничего не менять)

В одном помещении без дверей/стен между игроком и приёмником, на одной
и той же высоте, поворачивать **только** камеру/персонажа на
0°, 90°, 180°, 270° на расстояниях 1, 3, 5 и 10 клеток.
Сравнить с Viewpoint ON/OFF на неизменной громкости устройства.
Повторить штатный CUE/test_tone, так как этот звук идёт через другой
GameSoundClip/FM0DSoundEmitter; музыка — через отдельный Java stream.

В отладочной *read-only* диагностике отдельно фиксировать:
- текущие координаты/частоту/громкость устройства, тип источника и
  положение FMOD listener (если API позволяет прочитать без патча);
- активный FMOD_3D режим, параметры min/max, spread и собственную gain;
- `FMOD_Channel_GetAudibility(long)`, если имеется. Это **оценка**
  слышимости с учётом части ослаблений, НЕ замер каналов на выходе;
- включён ли программный/аппаратный 5.1/7.1, виртуальный surround,
  и соответствует ли конфигурация реальным наушникам/динамикам.

Если оценка audibility почти постоянна, а фактический звук резко
пропадает, сначала исследовать speaker routing / panner / Viewpoint.
Если падает именно audibility, проверить attenuation/occlusion/DSP,
а не добавлять стереофайл вслепую. Сигнатура
`FMOD_Channel_GetAudibility(long)` описана для старой JNI,
на Build 42.21 нужна повторная проверка.

## Если дефект подтверждён: эксперимент A (первый выбор)

**Только клиентский Java bridge**, исключительно для
`station` источника вида furniture/vehicle:

1. Попробовать опционально найти
   `FMOD_Channel_Set3DSpread(long,float) -> int` через reflection.
   Метод не должен становиться обязательной зависимостью
   для базовой музыки: при отсутствии — прежний FMOD_3D без падения.
2. После создания 3D-канала, до начала слышимого воспроизведения,
   установить spread из проверенного диапазона. Начальный A/B:
   **0°, 60°, 90°, 120°** (подстройка только в тестовой сборке);
   0 — базовый/проверочный, **90° — гипотеза**, не утверждённая настройка.
   Не применять 360°: можно уничтожить правильную локализацию.
3. `FMOD_3D` остаётся включён; НЕ использовать
   `set3DLevel<1` (смешение 3D/2D), НЕ создавать вторую копию
   звука и НЕ переносить координаты источника к камере.
   Min/max останутся 4/12 после предыдущего PR-эксперимента.
4. Сравнить углы при неизменных координатах без перехода на другие
   WAV. Проверить, что спереди радио по-прежнему локализуется,
   сзади оно **слышно**, а за стеной не теряется разумная окклюзия.
5. При FMOD ошибке/отсутствии optional method не включать новый режим.
   Никакой циклической перезагрузки трека, сетевого запроса или обхода
   основного player-volume контроля.

Java/JVM mock: точное отражение method ABI, FMOD_RETURN=0,
границы 0..120, сохранение FMOD_3D и x/y/z, one-stream invariant,
отсутствие дополнительных create/release при повороте.
Lua mock: источник мебели/авто не меняется на 2D и не следует за
listener, seek/re-entry/retune корректны.

**Оценка накладных расходов:** одна операция установки spread при
открытии трека плюс штатный DSP pan, без дополнительных PCM-каналов
на диске, аудиофайлов и сетевого потока. Реальное отличие CPU
мерить по процессу игры, а не выводить из одного unit test.

## Если эксперимент A не помогает

### B. Проверить правильность listener/speaker mode

Сопоставить stereo output с реальными наушниками, настройками
пространственного звука ОС и режимом 5.1/7.1. Проверить, есть ли
пропадание у других штатных 3D-источников. Если их поведение
совпадает и зависит именно от Viewpoint, менять **глобальный**
`FMOD_System_Set3DListenerAttributes` в SiegerRadio опасно:
это сломает звук зомби, окружения и остальных модов.
В таком случае обсуждать исправление Viewpoint либо изолированный
radio-only DSP-способ после измерений; не перехватывать глобальный
listener без отдельного согласования.

### C. Только если нужен реальный стереофонический музыкальный образ

При наличии ОРИГИНАЛЬНЫХ аудиофайлов, где сохранились разные L/R,
сделать тестовое стерео WAV на одном треке, с тем же временем и
PCM sample rate, затем повторить FMOD_3D Spread 0/60/90/120.
**Копия моно в два одинаковых канала не восстанавливает потерянную
стереомузыку** и лишь увеличивает объём/работу без нового содержания.
Не перезаписывать текущие SHA каталогов автоматически.
Для масштабирования на 41 трек при 22050 Hz/16bit размер
несжатого PCM почти удвоится (~400 -> ~800 МиБ), увеличится
потоковый трафик с локального диска и потребление DSP CPU.
В случае подтверждения эффективности пересмотреть лимиты pack,
хеши, имена, runtime_revision/handshake и верификацию аудио;
сервер не должен отправлять звук по сети.

### D. Если нужна только радиоселективная компенсация «сзади»

Крайний вариант — **не 2D**, а ограниченная плавная коррекция
громкости только radio-канала на расстоянии 1–3 клеток
по ориентации слушателя. Нельзя делать это без информации
о стенах/комнатах: усиление окклюдированного источника из-за стены
сломает правдоподобие и может увеличить слышимость через препятствия.
Если есть проблема speaker routing, простое усиление gain может вообще
не помогать. Не использовать без отдельного подтверждения.

## Критерии приёмки

- Не менее одного и того же уровня разборчивости музыки у приёмника
  при 0/90/180/270°, без почти полной тишины сзади. Сохраняются
  физическая 3D-локализация, направленность, затухание к 12 клеткам.
- Реакция на выключение, нулевой volume, смену частоты и возврат
  сохраняется, один stream на клиента, без фонового PCM.
- CUE и голосовые/радиосообщения не деградируют, панорамирование
  зомби и остального мира не затронуто.
- Два клиента: одинаковая позиция эфира, без двойного звучания,
  ошибок JavaFMOD и заметных FPS/RAM-регрессий.
- При отсутствии native spread API клиент может пользоваться
  безопасным исходным FMOD_3D без экспериментальной ширины.
- До подтверждения владельцем **ничего не включать по умолчанию,
  не переделывать 41 WAV, не мержить PR и не развёртывать на VPS**.
