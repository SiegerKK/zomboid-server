# Сетап лагеря: один этап строительства и одна поставка

`pz story build setup` последовательно вызывает уже существующие
`constructionctl` и `batchctl`. Новый серверный модуль, игровой протокол,
служба, автоматическая загрузка чанков или переписывание мира не добавляются.
Команду запускают через `pz`, чтобы его общий lock удерживался до конца
операции. Дополнительный файловый lock не допускает два одновременных
сетапа одного поселения. Координаты конкретного лагеря остаются в приватных JSON.

## Входные данные и предварительный просмотр

```bash
sudo pz story build setup camp_copy \
  --source-world story_test \
  --file /root/camp/stages_build.json --stage phase01 \
  --batch /root/camp/phase01_items_batch.json \
  --batch /root/camp/phase01_liquids_batch.json
```

Без `--yes` выполняется только локальная компиляция. Не создаются игровые
запросы, журнал сетапа или резервная копия; игровые API не вызываются.
Выводятся точные количества операций и SHA-256 транспорта.
`--batch` повторяется: все выбранные файлы объединяются в **один** обычный
batch, чтобы сервер проверил их суммарную вместимость до первой выдачи.
Снабжение допускает только `container/add` и `ground/add`, не правит игроков,
автомобили, тела и не удаляет существующие предметы.

`--source-world` нужен только для явно выбранной копии с другим именем:
все входные файлы обязаны иметь один указанный исходный мир. Меняется лишь
поле `world` в производных приватных файлах; исходники и координаты не
переписываются. Команда **не создаёт, не выбирает и не запускает** копию мира.
Реальный Docker/save mount сверяют прежние проверки модулей.

## Применение

```bash
sudo pz story build setup camp_copy \
  --source-world story_test \
  --file /root/camp/stages_build.json --stage phase01 \
  --batch /root/camp/phase01_items_batch.json \
  --batch /root/camp/phase01_liquids_batch.json \
  --survey /root/current-camp-copy.json \
  --backup /srv/zomboid/backups/worlds/camp_copy/world-EXISTING.tar.gz \
  --allow-existing --yes
```

`world-EXISTING.tar.gz` обозначает **уже существующий** архив менеджера,
не готовое имя файла. Используется прежняя `livectl.checksum_backup`:
проверяются каталог выбранного мира и SHA-256 по sidecar. Архив не создаётся
на ходу, не восстанавливается; сервер не останавливается. Оператор заранее
обеспечивает корректный холодный checkpoint и рабочую копию мира.

Обязателен **новый полный AreaScan выбранного мира**: целевые клетки должны
быть загружены, а существующие окна и контейнеры — соответствовать точным
селекторам планов. Неизвестные/незагруженные клетки не считаются свободными.
Мозаику можно использовать по прежнему формату и правилам provenance.
Рекомендуемые категории: `squares,objects,containers,items,windows`.
У AreaScan нет доверенного времени съёмки: программа проверяет структуру,
покрытие и идентичность, а не доказывает актуальность по mtime. Старый снимок
нельзя просто переименовать или переписать в нём поле world.

Точные индексы существующих объектов автоматически не меняются. Если они
изменились, нужно сверить и исправить приватные планы **до первого запуска**.
Окно с уже имеющейся баррикадой или без поля проверки `windows` отклоняется.
Новые склады выбранного этапа разрешены как будущие цели только по точной
метке планируемого `storage`, координатам, индексу контейнера 0 и типу `crate`.
После строительства их наличие проверяет серверный batch, а не прогноз.

Порядок: предварительные проверки → строительство одного этапа → точная
полная квитанция и запись нативного журнала → единая поставка → её точная
полная квитанция. Любая ошибка останавливает цепочку. Ожидание ограничено
`--timeout 1..600` секунд **на запрос** (по умолчанию 120); это не обещание
времени исполнения в игре. Неопределённый результат не засчитывается как успех.

## Журнал, продолжение и повторный запуск

Приватные файлы находятся в:

```text
worlds/WORLD/story/setup/SETTLEMENT/STAGE/
  build.json    # точный план с выбранным миром
  stock.json    # объединённые поставки
  receipt.json  # намерение, ID запросов, SHA, полные ответы, сведения о backup
```

Перед очередью намерение записывается на диск. После отправки сохраняется ID,
а квитанции проверяются по ID, digest и **applied == total == requested**.
`server_applied` означает подтверждение сервера, не игровую приёмку.
Повтор успешного сетапа не строит и не выдаёт ничего заново. Обычный прямой
`pz story batch apply` по-прежнему не становится идемпотентным.

`--status` читает журнал без выдачи запросов. При тайм-ауте повторяют ту же
команду и те же входные данные с `--yes --resume`: программа ждёт **ранее
сохранённый ID**, а не отправляет его заново. Уже подтверждённое строительство
не повторяется. Если предыдущий запрос вернул error, канал был заменён,
план изменён, либо процесс оборвался между намерением и записью ID,
автоматическое продолжение запрещается. Не стирайте журнал ради обхода:
нужны осмотр мира и отдельное решение по восстановлению. Отката нет.

Зависимости `requires` должны совпасть с нативным build ledger **и** иметь
подтверждённый сетап с поставкой. Ранее вручную построенные стадии программа
не «усыновляет» и не снабжает молча. При клонировании или восстановлении
сохранения нельзя переносить старый setup-журнал как доказательство запасов
в другом состоянии мира. Потерянный/изменённый нативный журнал блокирует повтор.

## Приёмка после применения

Снять новый полный post-stage скан, затем использовать точный сохранённый план:

```bash
sudo pz story build verify camp_copy \
  --file /srv/zomboid/worlds/camp_copy/story/setup/example_camp/phase01/build.json \
  --stage phase01 --survey /root/post-phase01.json
```

`example_camp` заменяется на фактический `settlement` из плана/вывода setup.
Проверка кроватей/стен/ящиков по свойствам и меткам остаётся существующей.
Снабжение дополнительно сверяют по свежим `items`/`ground` и фактическим
литрам/калориям. Сетап не обещает автоматически пересчитать съедобность,
питьевое качество и необходимый многонедельный резерв.

Сцена `survival_farm` теперь планирует реальные крытые
пристройки к **основному дому** на III–IV этапах: для нового крыла
используется нативный `addFloor` этажом выше, плюс настоящие
двери и окна. Это всё ещё **не гарантия `IsoRoom`** и сухости
в B42.21 — требуется клиентская проверка крыши, пути между
домом и пристройкой, закрытости и двухклиентской синхронизации.
Генераторы остаются выключенными, не создаются грядки, коллекторы
или широкие ворота. Внешние отдельно стоящие постройки из
прежнего плана отменены; полное описание
[в отдельном обзоре](FARM_HOUSE_ANNEX_B42_RU.md).
Видимость, взаимодействие, сон, коллизии и сохранение после рестарта
проверяются в настоящем B42.21, а не только mock-тестами.
