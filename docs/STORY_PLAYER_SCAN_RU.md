# Story Director: сканирование предметов вокруг подключённого игрока

**Статус:** read-only скан проверен на фактической Build 42.21.0 в `story_test` (17 октября 2026). Он не создаёт предметы и не изменяет `road_home`. Клиентская проверка применения сюжетной сцены пока не выполнена.

## Почему старый инспектор не нашёл шкаф

Команда `pz story inspect` создаёт заранее фиксированный список точек. Изначально `story_test` проверял только **25 конкретных клеток** (X=3175..3179, Y=12113..12117, Z=0). Если игрок подошёл к шкафу за пределами этого квадрата, он не попадает в список. Это не 25x25 клеток и не следование за игроком.

## Новый режим (ровно 25×25×5)

Теперь после установки серверного runtime можно отправить запрос по **точному игровому логину**:

```bash
sudo pz story scan-player story_test kyrylo --yes
# Спустя несколько секунд, пока игрок ещё онлайн:
sudo pz story scan-status story_test
# Полный список в JSON (можно дать Codex/ChatGPT как файл):
sudo pz story scan-report story_test --output /var/tmp/story-clinic-scan.json
# Либо без нового файла:
sudo pz story scan-report story_test --json
```

- Центр берётся **не из терминала или старых координат**, а из `getOnlinePlayers()`, **один раз при поступлении запроса**. Игроку не нужно видеть/сообщать координаты. Движение во время сканирования не двигает центр.
- `25×25` = от `X-12..X+12`, `Y-12..Y+12` включительно.
- `5` уровней: обычно `Z-2..Z+2`; у крайних уровней границы сдвигаются, чтобы оставаться в допустимой шкале `-2..16`. На поверхности (Z=0) это `-2,-1,0,1,2`.
- Это **3125 кандидатов клеток**, а не гарантированно 3125 загруженных клеток. Сервер использует `getCell():getGridSquare()`, **не `getOrCreateGridSquare()`**; не заставляет загрузить и не изменяет отсутствующие чанки. Отчёт содержит `loaded_squares`/`unloaded_squares`.
- По 20 клеток за тик, одноразово по запросу. Между запросами остаётся дешёвая проверка файла раз в 120 тиков. На большой заполненной локации есть ограничение в 90 000 записей/24 MiB и флаг `truncated`.
- Не открываются RCON/HTTP/Docker TCP порты, нет клиентских команд или arbitrary Lua evaluation.

## Данные отчёта

JSON с `meta`, `summary`, `records`. Каждая запись с координатами `x,y,z`:

- `kind=object`: объект стены/двери/мебели, его `object_index`, `sprite`, `class`, `room`.
- `kind=container`: контейнер внутри объекта, `object_index`, `container_index`, `container_type`, `item_count` (включая **пустые** шкафы).
- `kind=container_item`: каждый предмет в контейнере с `full_type`, `name` и индексом слота.
- `kind=ground_item`: каждый предмет на полу и его координаты.
- `kind=static_object`: статические объекты (например трупы) и, если они доступны через API, их контейнеры и вещи.

**Текущие ограничения:** это снимок содержимого уже загруженного мира, а не вся карта на диске. Он не обходит личные инвентари игроков, закрытые/незагруженные клетки или автомобильные багажники. Эти категории можно добавить отдельным проверяемым адаптером. `instanceof`/видимые свойства используются только в дальнейшем для точных селекторов сцен; сам скан не меняет содержимое.

Отчёт также может отметить `status=partial`, `errors>0` или `truncated=true`. Полноту обхода и покрытие карты нужно различать: `complete` означает проверку всех кандидатов без ошибок и усечения; nil-клетки учитываются отдельно и не считаются осмотренными объектами. При смене обстановки индекс объекта в клетке может измениться, поэтому перед изменениями всё равно проверяйте `sprite` и `class`.

## Протокол на сервере

В выбранном слоте:
```text
/srv/zomboid/worlds/<slot>/data/Lua/
    SiegerStoryScanRequest.txt
    SiegerStoryScanResult.txt       # JSONL inside; .jsonl is forbidden by B42 writer
    SiegerStoryScanProcessed.txt    # completed ID; no replay after runtime restart
```

Запрос создаётся локальным **root-only** `sudo pz story scan-player` с случайным ID. Lua читает только фиксированное имя файла, строго ограниченный формат и размер, находит точный игровой `username`. Результат пишет штатным `getFileWriter`. `scan-report` откажется выдать старый/незавершённый результат без совпадения ID и строки `summary`. Следующий запрос допускается только после завершения предыдущего. Файлы находятся отдельно для каждого мира, в `/root/Zomboid/Lua`.

Никаких следящих демонов, Java plugins, новых Workshop-модов и перезапусков ради **каждого** запроса. Но чтобы установить **новый серверный Lua runtime**, первый раз нужно корректно пересоздать контейнер в согласованное окно.

## План безопасной установки для Codex

1. Прочитать PR #6 и новую ветку `feature/story-player-area-scan`. Не переписать работающий `road_home` старым `main`. Ветка сканера основана на последней интеграции PR #6.
2. Проверить `bash -n pz`, `python3 tests/test_story_area_scan.py`, `lua5.1 tests/story_area_scan.lua story/runtime/SiegerStoryAreaScan.lua`, Lua syntax/Compose CI; убедиться, что новые mount только read-only, рабочие 12 GiB/UDP/Workshop сохранены.
3. Дополнительно проверить в **реальном pinned `projectzomboid.jar`** наличие `getFileReader/getFileWriter`, `getOnlinePlayers`, `getContainerCount/getContainerByIndex`, `getWorldObjects`, `getStaticMovingObjects`, `getGridSquare`.
4. В согласованное окно при `players=0` создать cold backup, запустить **только `story_test`** с обновлённым read-only mount. Не разворачивать сканер на `road_home`, если у него нет Story bundle.
5. Игрок заходит в клинику. Выполнить `sudo pz story scan-player story_test <его_игровой_логин> --yes` **пока он в игре**, дождаться отчёта, экспортировать JSON.
6. Найти реально существующие `container` записи в `edclinic` и привязать подтверждённые `x,y,z,object_index,sprite,class` к сцене. Не менять `clinic_last_shift.json` вслепую. Если нужен `container_index>0`, отдельно добавить/проверить поддержку вторичных контейнеров в селекторах Story Director.
7. Вернуть `road_home` после проверки. Только после успешного smoke-test решать, мержить ли эту ветку в PR #6 / main.

Отчёты не загружать публично на GitHub, если в них есть содержимое личных записок, приватные имена персонажей или координаты личных тайников.

## Ревью pinned Build 42.21.0 перед установкой

Проверены реальные классы закреплённого image из PR #6. `getOnlinePlayers()`
имеет серверную ветку `GameServer.getPlayers()`. `getFileReader(String,bool)`
и `getFileWriter(String,bool,bool)` используют Lua cache directory выбранного
`/root/Zomboid` mount. **Writer разрешает только ini/cfg/txt/log/json**:
исходное имя `.jsonl` отвергалось бы. Формат остаётся JSON Lines, файл теперь `.txt`.
`LuaFileWriter` поддерживает write/close; API container count/index и списков
клетки присутствуют. Подтверждена база PR #6, игровые config/scripts не заменены.

После ревью добавлены ограничения и проверки:

- Не более 20 клеток **и 200 шагов обхода объектов/предметов за тик**.
  Переполненный инвентарь продолжается coroutine на следующих тиках.
- Усечение/слишком длинное поле завершают запрос как `partial`, без скрытого
  обрезания названий. Ошибки getter-ов входят в `errors`.
- Полный footer, ID, exact username, число записей и суммы счётчиков проверяются
  Python. `partial/error` дают ненулевой exit code, но диагностический JSON
  можно сохранить. `pending` не выдаётся за готовый экспорт.
- Persistent completed ID не даёт перезапуску runtime повторить старый запрос.
- Экспорт запрещён внутри source repository; файлы экспорта создаются с 600.
- Класс определяется через exposed `instanceof` известных типов. В реальной
  игре `getClass():getSimpleName()` пишет исключения даже внутри pcall, поэтому
  этот путь исключён. Базовый `IsoObject` не обещает точное имя Java-подкласса;
  неизвестный класс отмечается ошибкой, не угадывается.

`unloaded_squares` означает **getGridSquare вернул nil**: это может быть
незагруженная клетка **или отсутствующая клетка**, например воздух без пола.
Сканер не различает эти причины и не загружает карту принудительно.
`complete` означает завершённый обход 3125 кандидатов без ошибок/усечения;
это не обещание 3125 существующих клеток. Фактическое покрытие всегда берётся
из loaded/unloaded. Снимок инкрементальный, не атомарный: игроку желательно
стоять на месте и не менять содержимое во время запроса. Вложенные сумки
не раскрываются рекурсивно (`inventory_scope=top_level_only`).

Lua 5.1 harness дополнен 1000 предметов в одном контейнере, защитой от replay,
видимостью partial и native Unicode fixtures. `tests/StoryKahluaCheck.java`
позволяет запустить тот же synthetic harness в Kahlua и JRE именно pinned
игры, **в отдельном контейнере, без запуска GameServer**. Имена предметов
в этом тесте передаются Java-строками, как из игрового API. Загружать Unicode
fixtures как Lua-литералы через Java loadstring некорректно для этого теста.
Компиляция: `javac --release 21 -d /tmp/story-vm-check tests/StoryKahluaCheck.java`.
В изолированном image, после копирования class в /tmp/story-vm-check и двух Lua файлов в /tmp:

```bash
/pzomboid-server/jre64/bin/java \
  -cp /tmp/story-vm-check:/pzomboid-server/java/projectzomboid.jar \
  StoryKahluaCheck /tmp/story_area_scan.lua /tmp/SiegerStoryAreaScan.lua /tmp/synthetic.jsonl
```

Результат synthetic JSONL дополнительно читается Python как UTF-8 JSON и
проверяется точное сохранение кириллицы и кавычек. Это **не** live-скан
клиники и не заменяет тест реальных engine userdata и файлового I/O.
Первый перезапуск story_test требует отдельного подтверждения владельца,
проверки players=0 и свежего cold backup. Первое обновление выполнено с подтверждением владельца, players=0 и проверенным cold backup.

## Результат первого клиентского сканирования — 2026-10-17

На VPS установлен commit `0d3d9d6` PR #7, перезапущен только `story_test`.
Оба публичных UDP-порта ответили внешнему probe; RCON работает внутри контейнера
и не опубликован. Основной `road_home` остановлен: SHA-256 всех 7223 файлов
совпал с манифестом до обновления. Workshop snapshot и ZombieBuddy read-only
mount сохранены; heap 8 GiB, лимит 12 GiB, после старта RAM около 9.25 GiB.

По запросу подключённого владельца проверены все **3125** кандидатов:
1157 существующих загруженных клеток, 1968 nil-клеток (незагруженные или
отсутствующие, включая воздух), 1743 объекта, 16 контейнеров, 20 предметов
в контейнерах, 19 предметов на земле, 1798 записей. Итог `complete`,
`errors=0`, `truncated=false`. Полный JSON хранится вне Git с правами 600
в root-only каталоге VPS; имена аккаунтов, полный инвентарь и координаты
скана в публичный отчёт не включаются.

Обнаружена отдельная проблема диагностики: Java Class.getSimpleName не
экспонирован в Lua. Каждый неудачный вызов писал stack trace в игровой лог,
хотя instanceof fallback завершил скан. Исправление убирает reflection
полностью; harness проверяет, что getClass не вызывается. Исправленный runtime
пока **не установлен на работающий сервер**: нужен следующий согласованный
перезапуск без игроков. Повторный скан до обновления не рекомендуется.

Черновик `clinic_last_shift.json` привязан к подтверждённому пустому
filingcabinet с primary container index 0; записка из трёх страниц, два бинта
и один дезинфектор направлены в один контейнер. Подтверждённое окно задано
для отключённой barricade action. Глобально сцена **disabled**, в bundle
не добавлена и **не применена**. Следующий этап — выход игрока, новый cold
backup, отдельное согласование применения и клиентская проверка содержимого,
сохранения и отсутствия дубликатов после рестарта.
