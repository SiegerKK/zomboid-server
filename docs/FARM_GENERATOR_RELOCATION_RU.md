# Генератор фермы: исправление охвата и явный перенос

Первый генератор II этапа переносится в будущих планах с
(9288,7759,0) на проверенную наружную клетку (9280,7771,0).
При GeneratorTileRange=20 радиус круговой, а не квадратный:
(dx²+dy²)<=400, вертикальный охват текущего сервера ±3.
Новая точка покрывает весь исходный дом x9274..9282/y7775..7785
и внутреннюю площадь нового крыла x9286..9296/y7768..7783.
Старый технический ящик остаётся у теплицы; содержимое не переносится.
В новой позиции генератор в сцене по-прежнему пустой и выключенный.

Для существующего мира добавлена узкая `move_generator` операция
строительного менеджера. Только одна операция в стадии, явный
--allow-existing, точный owner-tag, класс IsoGenerator, исходный sprite,
две загруженные клетки одного этажа, наружное свободное место с полом.
Нет произвольного Lua, принудительной загрузки чанков или удаления
инвентарей. Старые receipts и первоначальная метка не переписываются.
Повторное выполнение завершённого stage запрещено.

Пример JSON action внутри обычного construction plan:

```json
{"id":"move_power","op":"move_generator","kind":"IsoGenerator",
 "at":[9288,7759,0],"to":[9280,7771,0],
 "sprite":"appliances_misc_01_0",
 "target_tag":"survival_farm:phase02:first_generator"}
```

Сохраняется тот же Java-объект, топливо, состояние, ModData и прежние
флаги подключения/работы. На время переноса он выключается и отключается,
исходная клетка передаёт native remove, затем setSquare и
AddSpecialObject регистрируют его в новой клетке; полная передача ровно
одна в новой точке, затем восстанавливаются флаги. Проверены реальные
API Build42.21: AddSpecialObject вызывает addToWorld и не делает полного
transmit; IsoGenerator.removeFromWorld снимает регистрацию и emitter;
setActivated пересчитывает электричество и sync. Предварительная
проверка повторяется непосредственно перед изменением.

При исключении после начала изменений результат partial_possible:
остановиться, инспектировать обе клетки, не повторять команду и не
восстанавливать автоматически backup. Перенос требует проверенного
холодного checkpoint, затем загруженных игроком клеток и независимых
сканов до/после. Это отдельная ремонтная стадия: phase02 не переигрывается,
новые предметы не выдаются. Штатный build verify предназначен для
построек; перенос проверяется точным tag/class/координатами и состоянием
по свежему AreaScan обеих клеток.

Автотесты проверяют сохранение идентичности/топлива/износа/флагов,
единственную отправку, replay, отказ для помещения/занятой клетки/нет
пола/чужой метки/отсутствия разрешения. Проверка на клиенте и реальное
питание приборов остаются отдельной приёмкой; CI не заменяет её.
