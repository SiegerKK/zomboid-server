# Наблюдение за поведением загруженных зомби по запросу

SiegerAdmin, Project Zomboid Build 42.21.0. Один репозиторий и Bash-команда `pz`.
Диагностика теперь использует точное имя выбранного активного Story-мира,
а не жёсткое `story_test`, чтобы снимки можно было совмещать с универсальным
Building Atlas из [SIEGER_ATLAS_RU.md](SIEGER_ATLAS_RU.md). Примеры ниже —
`story_test` как один из поддерживаемых миров.
Это read-only наблюдатель: не вызывает AI-функции мода, setters, GetZType,
GetNonPersistentZData, pathToSound, принудительную загрузку чанков или Lua eval.
Радио, Workshop и сохранённые данные зомби не изменяются. Клиентского канала
команд нет: запрос создаёт оператор CLI в приватном каталоге выбранного мира.

## Команды

```
sudo pz story zombies snapshot story_test --player LOGIN --yes
sudo pz story zombies status story_test
sudo pz story zombies report story_test --output /var/tmp/zombie-snapshot.json

sudo pz story zombies record story_test --seconds 120 --interval-ms 1000 --player LOGIN --yes
sudo pz story zombies status story_test
sudo pz story zombies stop story_test --yes
sudo pz story zombies report story_test --output /var/tmp/zombie-recording.json
sudo pz story zombies analyze story_test --output /var/tmp/zombie-analysis.json
```

`--player` необязателен: задаёт только точку отсчёта расстояния, не ограничивает
список зомби и не требует присутствия игрока для самого сбора.
Для указанного игрока записываются доступные флаги invisible/ghost/god,
sneaking/running/sprinting: они важны для интерпретации реакции заражённых. Точное отсутствие
игрока в очередном кадре даёт anchor=null. Без `--yes` snapshot/record/stop —
preview. `stop` останавливает только запись, не игровой сервер.
Для codex-pz используйте тот же существующий `pz-vps story zombies ...`, вывод
`--output NAME.json` попадёт в `/var/lib/pz-codex/exports` с правами 600.

Длительность — **реальные**, не игровые секунды, 1..1800. Интервал —
100..60000 мс, по умолчанию 1000 мс. Измерения выполняются целиком по всему
текущему server zombie list. Они не распределяются по нескольким игровым
кадрам и не ограничиваются расстоянием до игрока. Пользователь явно допускает
нагрузку для этого отладочного режима; один полный замер может задержать tick.

По умолчанию: 64 МиБ, 250000 JSONL-строк, до 10000 слотов в одном замере.
Явно доступны `--max-mib 1..256`, `--max-records 100..1000000`,
`--max-zombies 1..100000`. Это границы отказа, а не скрытое сэмплирование.
При превышении запись заканчивается `limited`: неполный результат не выдаётся
за complete. Длинная запись большой популяции может упереться в объём раньше
срока; увеличьте лимит или интервал. Невозможно прервать середину синхронного
Lua-прохода; фактическая длительность/задержки будут видны в отчёте.

## Формат и жизненный цикл

Запрос: фиксированный приватный `SiegerAdminZombieDebugRequest.txt`, v1.
Статус: `SiegerAdminZombieDebugStatus.txt`; stop содержит только текущий ID.
Результат каждого запуска — отдельный `SiegerAdminZombieDebug-<32hex>.txt`.
Внутри **JSON Lines**, расширение .txt совместимо с ограничениями GameTime Lua
file writer. Файлы не являются исполняемым Lua. Имена не берутся из произвольных
путей или клиентского ввода. Данные включают координаты и считаются приватными.

Запрос живёт 30 секунд; один активный сборщик. Durable guard до старта
предотвращает повторный запуск после сбоя/рестарта. После перезапуска running
помечается interrupted; исходный префикс журнала сохраняется без дописывания
выдуманного завершения/счётчиков, и запись автоматически не возобновляется.
После limited/error/interrupted новый запуск требует `--acknowledge-failed`.

Состояния: pending, running, complete, stopped, limited, error, interrupted.
status также отмечает просроченный запрос и устаревший heartbeat. Это признак
проблемы, а не доказательство исправного продолжающегося сбора.
Запуск CLI ставит запрос и сразу возвращает управление/lock pz: не держит
SSH или глобальную блокировку на весь период записи.

Результат обрамлён start, sample/записи/sample_end и end. Coverage каждого кадра
сверяется по inspected + null_slots + errors = expected_slots; NULL, ошибки,
пропуски и лимиты явные. Для complete нужны закрытые полные кадры и footer.
`report/analyze --allow-partial` позволяет изучить прерванный префикс, сохраняя
capture_complete=false. Остальные операции требуют действительно полного
результата. Экспорт отказывает на существующем пути/ссылке/пути в репозитории.
Старые записи читаются с `--id 32HEX`; новые записи их не перезаписывают.
Автоматического удаления/ротации нет. Журналы входят в cold backup полного
world/data; учитывайте их размер и храните только нужные контрольные записи.

В idle выполняется только небольшой опрос управляющих файлов раз в секунду.
Никаких zombie list проходов, постоянных per-zombie hooks или фона после конца.
OnTickEvenPaused позволяет работать и на пустом PAUSE_EMPTY сервере, но в этом
случае AI/игровое время могут стоять: неподвижность не считается ошибкой AI.

## Что сохраняется

- Часы реального времени в миллисекундах без округления до секунд, дата/часы
  игры, worldAgeHours, nightStrength, количество игроков, фактические sandbox
  флаги и уже инициализированные параметры TLOU.
- Устойчивый tracking_id для объекта в пределах одной записи; сетевой ID
  отдельно. Совпадение или повторное использование online_id не склеивает
  разных зомби. После выгрузки/нового объекта непрерывность не гарантируется.
- Тип только из существующего Forge cache; неизвестный остаётся unknown.
- Координаты/этаж, здоровье, alive, moving, state/previous_state, crawling,
  on_floor, useless; доступность текущей клетки, здание/комната по bounds,
  цель с типом/координатами/сетевым ID, thumping, путь/цель/длина/отмена,
  доступный владелец сетевого AI и таймеры обнаружения плоти/звука.
- Неизвестные getters дают null/unavailable, а не нули или ложное «снаружи».
  Имена других игроков, их инвентарь и весь modData не копируются.
- Вход/выход из загруженного списка. Потеря наблюдения — не смерть. Даже
  увиденный alive=false — наблюдаемое состояние, не полная история всех смертей.

Данные — серверное наблюдение. Часть AI может принадлежать клиенту: сервер
не обязан иметь все его локальные таймеры, подробности пути или намерения.

## Проверка HideIndoors

В закреплённых исходниках TLOU функция назначена Stalker/Clicker/Bloater,
не Runner. Если заражённый уже в здании, имеет цель или движется — пропуск.
Проверка также зависит от таймера и периодического tick-слота.
При nightStrength<0.5 либо WanderAtNight=false выбирается здание; иначе
бродячая точка снаружи. Уже находящегося в здании ночь наружу не выгоняет.
Поиск возвращает первую найденную клетку здания, не доказанно ближайшую или
достижимую. Наличие маршрута не гарантирует проход через двери/препятствия.

Поле hide_rule **только вывод по прочитанным условиям**, а не перехват решения.
Записываются bound, branch, eligibility и timer_gate. Tick-слот/клиентское
владение AI и прочие причины маршрута могут не наблюдаться. Никакие функции
поиска здания/управления зомби ради диагностики не вызываются.

`analyze` выводит:
- историю состояний, число наблюдений внутри/снаружи/с целью/в движении;
- переходы между состояниями, зданиями, целями и путями;
- потери наблюдения; перемещения/скорость только между соседними кадрами без
  пробелов (не через выгрузку или ошибку);
- сводку по типу/дневной-ночной ветке, условию пропуска HideIndoors;
- stationary_path_candidate после 10 реальных секунд почти без смещения
  при признаке пути и увеличении игрового времени. Это кандидат для разбора,
  не доказательство сломанной навигации. Во время паузы такой вывод не делается;
- число совпадающих online_id в одном кадре без удаления записей;
- elapsed_ms самого замера, задержки, пропущенные интервалы и полноту кадров.

История включает все исходные снимки; events анализа производные. Лимит
производных событий по умолчанию 5000 (`--events-limit 0..100000`), усечение
помечается events_truncated и не уничтожает исходные данные. Анализ ограничен
200000 уникальными объектами и явно отказывает при превышении, оставляя trace.
Число внутри — доля снимков, не точное время пребывания в здании. Движение —
нижняя оценка длины по точкам. Без дополнительных наблюдений нельзя приписать
вход в здание именно HideIndoors вместо погони за игроком или реакции на звук.

## Практический эксперимент

1. Выбрать загруженную область со Stalker/Clicker и зданиями. Не привлекать
   заражённых выстрелами, клаксоном, светом и своим присутствием.
2. Записать 60..180 секунд при дневной ветке. Runner — контрольная группа.
3. Если владелец разрешит смену часов, перейти к ночи и дождаться изменения
   nightStrength; снова записать период. Один скачок часов не симулирует часы
   движения, погоду или навигацию. Не менять модпак в ходе эксперимента.
4. Сравнить отдельные tracking_id в непрерывной записи либо явно разделённые
   сессии. Не считать одинаковый сетевой ID доказательством той же особи.
5. Проверять условия допуска, выбор пути и фактический переход внутрь отдельно.
   При работе с двумя клиентами добавить проверку расхождений наблюдений.

## Автоматическая и игровая приёмка

Lua 5.1 + Python fixtures: idle без обращения к миру, два объекта с одинаковым
online_id, вход в здание/смена состояния, исчезновение, getter errors, optional
unknown, длительность, stop/pending stop, byte/row/zombie limits, restart без
resume, приватный экспорт, полнота и повреждённые/прерванные журналы.
API проверены по установленному реальному projectzomboid.jar B42.21;
getPathFindBehavior2 — чистый getter уже существующего поля. GetZType не вызывается.
Fixture также выполняется точной Kahlua VM установленной игры; это проверка
Lua/формата с моделями объектов, а не доказательство настоящего поведения AI.

BLOCKED до согласованного развёртывания и обновления клиентского SiegerAdmin:
реальная запись работающей JVM, корректность доступных полей на серверных
зомби, нагрузка на большой популяции, клиентский checksum login и подтверждение
дневного/ночного поведения. PR не мержить и сервер не перезапускать автоматически.
Радиопакет/музыка не меняются; нужен только соответствующий клиентский Admin.
