# Исправление 3D-радио после клиентской видеопроверки

## Статус

Версия `sr17-v1-9c6afcc4b253`, runtime_revision=8, PR #24.
Предыдущий вариант Spread=120 не прошёл игровую приёмку владельца.
Новый код и пакет подготовлены; **в работающую игру и на VPS не установлены**.
Повторное прослушивание и езда с реальными клиентами обязательны.

## Что подтверждено

- Локальная запись 108.768 s, 1920×1080, stereo AAC 48 kHz. Есть осмотр
  машины, вращение взгляда и поездка. Видео/извлечённое аудио остаются локально.
- В первых секундах распознана north_track_09 (корреляция ~0.794 с оригиналом).
  Оценка вклада этой музыки в смешанный игровой звук падает примерно на 30 dB
  около 42–49 s. Это оценка из записи с мотором/окружением, не прямой замер FMOD.
- Живой PulseAudio поток ProjectZomboid64: **6ch / 32000 Hz**,
  FL/FR/FC/LFE/SL/SR. Выход наушников — **2ch / 48000 Hz**, FL/FR,
  без перекоса уровня L/R. Настройки звуковой системы не менялись.
- Реальный native FMOD_System_Init PZ задаёт software speaker mode=6 (5.1).
  Viewpoint Hearing.listen переориентирует listener через Studio Listener3D.
- На настоящем libfmod 2.03.09 источник сзади при native 5.1 даёт сигнал
  в SL/SR, а не FL/FR. Это подтверждённый маршрут риска при выводе в наушники;
  конкретные коэффициенты системного downmix пока не измерены. Само наличие
  5.1→2 не доказывает дефект любого PulseAudio downmix.
- Spread=120 разносит компоненты stereo на ±60° вокруг точки источника:
  отсюда возможны искусственные направления музыкальных партий. Это не
  компенсация rear attenuation. Старую попытку не считать исправлением.
- В прежнем Lua координаты машины обновлялись вместе с дорогим поиском радио
  раз в 30 ticks (~600 ms при 50 FPS). Движущийся listener обгонял старую точку
  источника: это согласуется с пропаданием на ходу и возвратом после остановки.
  В старом логе нет native-stream errors, но нет и достаточных start/stop
  метрик, чтобы утверждать, что каждый обрыв был только затуханием.

## Новый локальный для SiegerRadio путь

Один FMOD_CREATESTREAM | FMOD_3D канал, физические X/Y и Z×3
(тот же масштаб этажей, что у штатного PZ listener/emitter), near/far=4/12.
Gain и окклюзия не меняются. Spread по умолчанию **0°**: одна физическая точка.
Два оригинальных канала файлов сохраняются; FMOD позиционирует 3D-точку
обычным способом. Portable остаётся прежним настоящим stereo FMOD_2D.

Для автомобильного/стационарного радио создаётся **одна частная mixer group**
SiegerRadioStereo. Её FADER получает channel format FL|FR / 2 / STEREO.
Это шина одного существующего потока, не второй музыкальный источник.
Не меняются устройство, глобальный software format, listener, Viewpoint,
звуки зомби/оружия/шагов/машин или master group.

В отдельной NOSOUND_NRT системе настоящей игровой FMOD (без аудиоустройства):

| Угол listener | Native stereo RMS L/R | Частная stereo-шина при global 5.1 |
|---|---|---|
| 0° | .1075 / .1075 | .1075 / .1075 |
| 90° | .1519 / 0 | .1556 / 0 |
| 180° | .1074 / .1074 | .0759 / .0759 |
| 270° | 0 / .1520 | 0 / .1558 |

Задний источник в частной шине слышим в обоих каналах; примерно −3 dB
относительно переднего, а не тишина. Это синтетический тест native DSP,
**не прослушивание модифицированной игры**. Контрольный посторонний источник
по-прежнему выдаёт сигнал только в задние SL/SR, global format остаётся 5.1.
То есть остальные игровые звуки не перенаправлены в stereo.

ПКМ при активном физическом радио → `SiegerRadio: output A/B`:
`Stereo headphones (3D)` / `Native surround (3D)`. Переключается группа
того же канала, без нового PlaySound/seek. Native оставлен для настоящего 5.1
и сравнения. Прежние Spread-предустановки оставлены как явная диагностика,
не как рекомендуемое исправление; основной тест проводить со Spread=0.

Если optional group/direct-buffer API отсутствует, остаётся native 3D с
`stereo_bus_unavailable`/`stereo_bus_failed`, а не ложный PASS.

## JNI: проверять семантику, а не только Java-сигнатуру

FMOD_System_PlaySound(long,long): второй аргумент — **paused**, не группа.
Новый поток стартует paused=1, затем настраиваются маршрут, позиция, seek
и уровень; только после этого SetPaused(channel,0). Это исключает стартовый
фрагмент песни с нулевой секунды.

FMOD_DSP_SetChannelFormat(long,long,int,long): mask и speaker mode в этом
старом SWIG JNI — **указатели на int32**, а не значения 3. Используется
ровно один приватный direct ByteBuffer(8), native byte order, проверенный
LWJGL MemoryUtil.memAddress; pointer outputs очищаются и проверяются.
Lua не получает указателей, путей, произвольных параметров DSP или классов.

При подготовке изолированного probe неверное предположение об enum pointer
в JNI SetOutput/SetChannelFormat вызвало SIGSEGV отдельного тестового JVM.
Исправлено до распространения: реальные вызовы прошли повторно, mock теперь
проверяет адреса и значения int32, а не ошибочно принимает литералы enum.
Запущенная игра и VPS этими пробами не затрагивались. Краш-логи локальные.

Проверено на установленном Linux B42.21.0; другую native ABI не считать
поддержанной по одному совпадению имён методов. Для Windows/macOS нужна
отдельная проверка клиента и актуальной библиотеки.

## Движение и ресурсы

- Сначала ищется радио `player:getVehicle()`; временно пустой Set машин
  на границе чанков и отстающие render-координаты героя не теряют его машину.
- Cached vehicle part проверяет питание/частоту/volume, координаты существующего
  FMOD источника обновляются **каждый tick**. Полный поиск остаётся throttled.
- JNI Set3DAttributes пропускается при неизменной позиции; SetVolume — при
  неизменном gain. Нет пересоздания или seek на каждом движении.
- Выключение/retune/потеря питания/слышимости освобождают канал, группу и sound.
  В возврате используется текущая позиция эфира. Portable без новой шины.
- STREAM START/STOP и SPATIAL/OUTPUT логи содержат тип/clip/offset/status,
  без координат баз и содержимого инвентарей.
- 41 музыкальный WAV побайтово неизменён; глобальная нагрузка не профилировалась.
  Добавлена одна mixer group/небольшой stereo buffer, а не второй декодер.
  FPS/CPU/RAM в реальной поездке всё ещё нужно проверить.

семантику, private bus, toggle и cleanup; это не тест modRoot/мультиплеера.

## Повторная игровая проверка и диагностическое дополнение (2026-10-18)

Владелец подтвердил секундные провалы **только музыки** при движении и на
стоянке. Переключение Stereo headphones → Native surround их не устранило.
Игровую приёмку прежнего исправления считать **FAIL**, причину пока не
считать установленной. Клиентский журнал показывает штатную смену трека,
но не фиксирует остановки/ошибки обновления во время сообщённых провалов.
Это не доказывает непрерывность native-воспроизведения.

Подготовлен локальный client-only DROPOUT-PROBE1 для каталога
`sr17-v1-9c6afcc4b253`. Каталог/handshake/музыка не менялись; сервер не
изменён. Дополнение — диагностическое, не исправление звука. Раз в секунду
пишется `SIEGER_RADIO_CLIENT TELEMETRY`: позиция песни в ms, audibility,
playing/virtual, количество/давность обновлений, open state, buffer percent,
starving/disk busy. Нет координат, инвентарей, путей или произвольных
FMOD handle/команд. Не меняет громкость, seek, режим или число потоков.
Ошибки optional getters не прерывают воспроизведение.

PASS: Java regression suite (включая starvation/read failure и отсутствие
побочных restart/seek), Lua 5.1 receiver harness (ограничение частоты и
ошибка probe), Python radio/station/pack tests, Lua syntax, diff check.
PASS: отдельная NOSOUND_NRT JVM с реальным игровым JAR и libfmodintegration64
Build 42.21.0: `pos_ms=1000 audibility=1.0 playing=true virtual=false
open_rc=0 open_state=6 buffer_pct=50 starving=false disk_busy=false`.
JNI ABI GetPosition проверен по native wrapper: второй long — значение
FMOD_TIMEUNIT_MS=1, результат — позиция, не output pointer. GetOpenState
использует четыре указателя на собственный direct buffer 16 bytes.
Мост собран JDK25 против установленного game JAR; тестовые классы в пакет
не попадают. Первый запуск сборки системным старым JDK не прошёл разрешение
LuaMethod; повтор правильным JDK25 прошёл, заглушки не использовались.

BLOCKED: сбор телеметрии при реальном провале — требуется установка
двухфайлового локального дополнения и перезапуск **клиента** владельцем.
В игровой процесс на ходу код не внедрён. VPS/игровой сервер не остановлены,
мир не менялся, музыкальные бинарники не публиковались.

### Результат PROBE1 и кандидат VOICE-FIX-PROBE2

В реальной игре получены 120 секундных замеров: 27 с `virtual=true`.
Есть последовательный интервал примерно 31–43 секунды песни: позиция трека
продвигается, audibility=0.5, virtual=true, буфер=70%, starving=false,
обновления источника продолжаются. Это подтверждает потерю реального
воспроизведения при живом потоке, а не вызов stop со стороны Lua.
Позже один замер показал starving=true при virtual=false; возможная
дополнительная причина ещё не исключена. Отсутствие starvation в первых
замерах нельзя распространять на всю сессию.

PROBE2 задаёт priority=32 только собственному музыкальному каналу перед
unpause. FMOD default=128; меньшее число означает более высокий приоритет.
Другие каналы, глобальный лимит, listener, громкость/3D и радиус прежние.
При нехватке реальных голосов один менее приоритетный голос может уступить
место музыке; в игровой приёмке проверить двигатель и остальные звуки.
Optional API unavailable/rejected даёт явный status без поломки обычного 3D.
Каталог и handshake сохранены: это локальная диагностическая сборка для
уже установленного `sr17-v1-9c6afcc4b253`, а не серверный релиз.

PASS: реальный JAR/JNI Build 42.21.0, отдельная NOSOUND_NRT JVM с двумя
реальными mixer voices и двумя конкурирующими громкими звуками default128:
тихая музыка default128 становится virtual, applyPriority32 возвращает
ТОТ ЖЕ канал без restart/seek. Уменьшение software-channel limit до двух
делается только в этом отдельном тестовом процессе, никогда в игре.
PASS: Java regression и missing/rejected priority fallback, Python
station/pack suites. Игровая слышимость PROBE2 остаётся **BLOCKED** до
установки владельцем и повторного заезда/стоянки. Сервер не менялся.

Документация механизма:
https://www.fmod.com/docs/2.04/api/managing-resources-in-the-core-api.html
(реальная ABI-совместимость проверена именно на установленном FMOD 2.03.09,
а не выведена только из документации версии 2.04).

### Чистый клиент voicefix-cabin1

Владелец подтвердил устранение прерываний после PROBE2: игровая приёмка
приоритета32 **PASS по сообщению владельца**. Это не означает завершение
новой приёмки звучания внутри салона.

Из runtime удалены периодическая TELEMETRY, диагностические JNI-getters,
дополнительный direct buffer и счётчики каждого update, временные меню A/B.
Оставлены редкие события start/stop/error и build/status при старте трека.
Исправление priority32 и обновление координат движущейся машины сохранены.

Введён `siegradioBridgeSetCabin(boolean)` для того же активного 3D-канала.
Только если локальный игрок находится в машине-источнике, используется
stereo spread180. При выходе/смене источника восстанавливается внешний
spread (по умолчанию0). Состояние проверяется без повторных JNI-вызовов
на неизменившихся кадрах. Стерео180 расширяет левую/правую части согласно
FMOD, не делает два потока и не подменяет мировую позицию. Стерео со
сильно неравными исходными каналами не нормализуется. Точного равенства
L/R для любого угла камеры это не обещает; в диагональных направлениях
синтетический тест показывает остаточную разницу до примерно5.5dB.

PASS: Java regression, optional missing/rejected priority fallback,
Lua5.1 syntax/client/receiver (вход/выход, один переход вместо per-frame,
нет меню A/B), Python radio/station/pack/stereo-prepare, 42 PCM hash checks.
PASS: реальная отдельная JVM/JNI42.21: конкуренция голосов, cabin180→outside0,
тот же канал и timeline, release, глобальный формат5.1 неизменен.
PASS: реальный libfmod2.03.09, isolated NOSOUND_NRT: synthetic440/660 stereo
при основных направлениях cabin180 даёт два канала с отношением RMS<1.05.
BLOCKED: игровая оценка новой ширины в Viewpoint при поворотах и езде.
