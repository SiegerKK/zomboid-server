# Sieger Story Director v1 — сценарии Project Zomboid из текста

Статус: **первый MVP** (проверяемые шаблоны и серверный Lua), не подтверждён живым двухклиентским тестом. Никакие сцены не активируются от одного лишь `git pull`. Подготовка и установка должны проходить через Codex в согласованное окно, на **копии** мира `road_home`. Общие сохранения и TLOU-моды не меняем.

Фактическая интеграция с PR #4, результаты VPS и оставшаяся проверка клиентом:
[STORY_DIRECTOR_DEPLOYMENT_RU.md](STORY_DIRECTOR_DEPLOYMENT_RU.md).

## Что работает в первой версии

- JSON-сценарии со списком операций, русским текстом и координатами игровых клеток `(x,y,z)`.
- Записки `Base.Note` с названием и несколькими страницами: на полу или **в точно проверенном** контейнере.
- Предметы и их количество: на полу или в указанном контейнере.
- Баррикады (1–4 доски) для уже существующего `IsoWindow` / `IsoDoor` / `IsoThumpable` **экспериментально**: требует `--allow-barricades` только после проверки конкретного объекта на тестовом мире.
- Read-only инспекция клеток: сервер пишет в журнал `SIEGER_STORY_INSPECT` с индексами, спрайтами, классами и контейнерами, **после загрузки нужного участка**.
- Idempotency: метка каждого применённого действия находится в `IsoGridSquare:getModData()` и синхронизируется; отдельные предметы также получают собственные метки. Повторный старт не должен дублировать уже успешно поставленные предметы.
- Точное разделение миров: собственный `story/bundle.lua` и собственный `compose.story.yaml` overlay только для выбранного мира.

### Пока сознательно не включено

- Принудительное создание `TLOU_Stalker` / `TLOU_Clicker`: Forge назначает ZType в зависимости от persistent outfit ID; обычный spawn зомби НЕ гарантирует нужный тип. Нужен отдельный **tested** Forge/TLOU адаптер, проверяющий визуал, повреждения, unload/reload и два клиента.
- Декоративные спрайты, стены, здания/крыши/целые карты: требуется проверка sprite ID, коллизий, локальной синхронизации и сохранения; **не** создавать вслепую через Lua на действующем мире.
- Автоматический «откат объектов» — не реализован из-за риска удалить уже забранные игроком вещи или тронуть чужую баррикаду. Откат целого мира — через `pz load` в **новый** слот после холодного backup.

## Формат данных

Источник истины: `story/scenes/clinic_last_shift.json`. Название файла равно `id`; `world` — фиксированное имя слота. У каждой операции собственный `id`, тип `note`, `loot`, `barricade`, `infected`, `decor` или `construction`. Последние три на production заблокированы (кроме `barricade` с дополнительным подтверждением).

В черновике `enabled=false`, неопределённые `x/y=null` и `VERIFY_FROM_STORY_INSPECT`: **это не реальные координаты/спрайты!** Нельзя применять пример, пока инспекция карты не определит фактические клетки и объект. Цифры карты B41 или произвольного скриншота нельзя считать проверенным Build42 миром.

## Команды

```bash
sudo pz story validate clinic_last_shift
sudo pz story preview clinic_last_shift
# Для реальной инспекции сперва остановить тестовый мир:
sudo pz story inspect story_test X Y Z --yes
sudo pz start story_test
sudo pz logs | grep 'SIEGER_STORY_INSPECT'
# Проинспектировать комнаты и подготовить точные индексы/спрайты:
sudo pz stop
sudo pz save story_test
# В story/scenes/clinic_last_shift.json заполнить реальные x/y и selector,
# поставить world=story_test и enabled=true, отключить пока не проверенные actions.
sudo pz story validate clinic_last_shift
sudo pz story preview clinic_last_shift
sudo pz story apply story_test clinic_last_shift --yes
sudo pz story status story_test
sudo pz start story_test
sudo pz logs
```

Для баррикад: `sudo pz story apply story_test clinic_last_shift --yes --allow-barricades` — только после отдельного безопасного test на выбранном окне/двери.

**Важно:** `inspect` и `apply` не перезапускают игру сами и работают только при остановленном контейнере. Для `apply` нужна доказанная SHA-256 холодная копия мира не старше четырёх часов, которую `pz save WORLD` создаёт на остановленном мире. Проверка `inspect` запустится, когда игрок приблизится и соответствующий участок мира загрузится. Она **не умеет читать всю карту без загрузки чанков**.

Псевдокоманды `pz story rollback` и `pz story spawn-tlou` в v1 **отсутствуют**, пока нет безопасного адаптера.

## Техническая схема

```text
story/scenes/*.json            ручной/ChatGPT текст
story/storyctl.py              Python standard library, строгий валидатор
story/runtime/SiegerStoryDirector.lua  серверный исполнитель PZ
compose.story.yaml             условные read-only mount, без внешних портов
/srv/zomboid/worlds/<slot>/story/scenes/*.json   снапшот
/srv/zomboid/worlds/<slot>/story/bundle.lua      сгенерированный Lua
```

`pz` использует существующий root-only flock и единый Docker Compose. Bundle генерируется экранированными строками и простыми литералами Lua, **никогда не включает произвольный код из JSON**. Серверный Lua файл не выполняется на игровом клиенте и не требует нового Workshop ID. При неудачной проверке `Story Director` отказывает, не пытаясь угадать контейнер.

### Проверка и развёртывание

1. Проверить последнюю версию `main`, изменения PR #4 и совпадение текущего развёрнутого commit. Не перезаписывать работающий world `road_home` или runtime `.env`.
2. Выполнить `python3 tests/test_story.py`, `bash -n pz` и Compose validation с тремя файлами: `compose.yaml`, `compose.mods.yaml`, `compose.story.yaml`. Проверить, что итоговый Compose сохранил весь список volume mounts, лимит 12g и только UDP порты 16261/16262.
3. В согласованное окно проверить `players=0`, сохранить состояние, сделать cold backup и восстановить в новый **disposable slot** `story_test`. Никаких `down -v`.
4. Выбрать клинику по карте Build 42; используйте отладочный клиент или `pz story inspect` для определения точных `x/y/z`, class/sprite/index. Не придумывать координаты.
5. Отредактировать JSON **только в проверенной репо-ветке**. Сначала на тесте активировать одну записку на полу и одну безопасную порцию лута, проверить в игре, сохранение, рестарт, отсутствие дубликатов; затем контейнер/баррикаду.
6. Тест двух игроков (предмет виден обоим, записка читается, содержимое шкафа одинаково, комната сохраняется). Если Java Lua API отличается на фактической B42.21, исправлять по журналу и повторно тестировать на копии, не включать небезопасные bypass.
7. Только после успешного теста и **отдельного подтверждения владельца** переносить approved scene на оригинальный `road_home`.

### Безопасность

Все world saves остаются вне Git. Тексты записок — публичный content repository: никаких реальных персональных данных, паролей, Steam токенов и секретов. Метки и SHA защищают от случайного повторения, **но не создают транзакцию** для игровых объектов и не заменяют cold backup. Запрещено автоматически очищать чанк, удалять существующих зомби/объекты игроков, изменять чужие предметы. При сомнении `abort`.

Ориентиры API B42: `IsoGridSquare.AddWorldInventoryItem`, `ItemContainer.AddItem`, `Literature.addPage`, `IsoBarricade.AddBarricadeToObject`, события `LoadGridsquare`, `OnTick`. Документы API не доказывают правильность net-sync в вашей конкретной модифицированной сборке: нужен реальный smoke-test Codex и два игровых клиента.


## On-demand area scan вокруг подключённого игрока (25×25×5)

Добавлен root-only `sudo pz story scan-player story_test GAME_LOGIN --yes`, который делает разовый структурированный отчёт об объектах, контейнерах и предметах вокруг *реальной текущей позиции* подключённого игрока. `sudo pz story scan-status story_test` показывает координаты первых контейнеров; `sudo pz story scan-report story_test --output /var/tmp/area-scan.json` выгружает все найденные строки для анализа и создания сценария.

Подробная инструкция: [STORY_PLAYER_SCAN_RU.md](STORY_PLAYER_SCAN_RU.md). Скан работает только при уже включённом Story overlay, без нового порта и без изменения карты; первый запуск нового runtime требует контролируемого перезапуска **тестового** контейнера. `road_home` автоматически не трогается.
