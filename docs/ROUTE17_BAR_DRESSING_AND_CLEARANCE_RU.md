## 1. Что показало видео (40 секунд)

В точках ~2–13 секунд видна регулярная дорожка из небольших предметов
по ковру между стульями и обеденными столами: бутылки, листки и прочие
мелкие вещи не используют поверхность мебели. В точках ~15 секунд видны
несколько заражённых внутри бара. После подъёма по лестнице та же
особенность проявляется в жилой зоне второго этажа.

Причина подтверждена старым кодом:
`square:AddWorldInventoryItem(item,0.5,0.5,0)`
во всех наземных `loot`/ `note` действиях. Теперь можно указать
точные смещения, высоту и ориентацию.

## 2. Новые координаты предмета

Произвольный `loot` или `note` может содержать:

```json
{
  "type": "loot",
  "id": "desk_bandage",
  "at": {"x": 10622, "y": 9228, "z": 0},
  "placement": "ground",
  "items": [{"type": "Base.Bandage", "count": 1}],
  "pose": {"x": 0.15, "y": 0.78, "z": 0.65, "angle": 37},
  "support": {
    "object_index": 1, "sprite": "furniture_tables_01_15", "class": "IsoObject"
  }
}
```

**Индекс/спрайт выше — условный пример; не применять без свежего скана.**
`pose.x`/`pose.y`: 0.05–0.95 доля клетки (можно у края);
`pose.z`: 0..0.90 (0 пол, ~0.65 столешница, высоту надо сверить
визуально по конкретной мебели); `angle`: 0..359 градусов.
Углы в отдельном генераторе постановки выбираются детерминированно по
хэшу Story-токена для естественно выглядящего разнообразия без прыжков
ориентации после рестарта.

При z>0 обязательны **точные индекс, спрайт и класс** реального
объекта, и сервер проверяет `isTableSurface()` и
`getSurfaceOffset()>0`. Если стол передвинут или его спрайт изменён,
операция завершается **без** спавна. Для пола `support` запрещён.
`placement=container` продолжает работать по-старому без `pose`.

Синтаксис без Git-коммита:

```bash
# Сначала DRY RUN:
sudo pz story apply-once story_test --key desk_bandage_001 \
  --type loot --x X --y Y --z 0 \
  --item Base.Bandage --count 1 \
  --purpose "Медицинская помощь у стола дежурного" \
  --offset-x 0.15 --offset-y 0.78 --height 0.65 --angle 37 \
  --support-index N --support-sprite EXACT_TABLE_SPRITE

# --yes добавлять только после dry run и проверки EXACT селектора.
```

## 3. Уже созданные предметы нельзя просто «переспавнить»

Новый `type=relocate` ищет **один существующий предмет по точному
SiegerStoryToken**, проверяет его исходную клетку и целевую поверхность,
сохраняет исходный InventoryItem и Story-маркировку, переставляет предмет
через серверные world remove+add API, а затем пишет `move` в журнал
исходного квеста. Старые вещи игроков не совпадают с токенами и не
подлежат перемещению. Расстояние ограничено 8 клетками на одном этаже.

```bash
# Пример, без --yes является предварительным просмотром:
sudo pz story apply-once story_test \
  --key restage_bar_note_001 --type relocate \
  --x FROM_X --y FROM_Y --z 0 \
  --token SiegerStory:smokeys_bar_01_public:dining_detail_01:1:1 \
  --to-x TABLE_X --to-y TABLE_Y --to-z 0 \
  --offset-x 0.17 --offset-y 0.78 --height 0.65 --angle 72 \
  --support-index N --support-sprite EXACT_TABLE_SPRITE \
  --allow-relocate
```

После ручной проверки можно повторить ту же команду с `--yes`.
**ОСТОРОЖНО:** удаление из исходной клетки и добавление в целевую
НЕ атомарны. При ошибке после удаления состояние может быть
неопределённым. Перед первой операцией делаем контрольный cold backup,
протестируем ОДНУ неважную Story-вещь и удостоверимся в стабильности
двух клиентов/сейва; никаких массовых перемещений до PASS. Флаг
`:spawn_attempted` блокирует повтор после неоднозначного сбоя.

Для генерации предварительного (НЕ применяемого) списка из реально
лежащих вещей:

```bash
sudo pz story scan-area story_test --player GAME_LOGIN \
  --center 10622,9221 --radius 25 --z-min 0 --z-max 1 \
  --include squares,objects,containers,items,ground,windows,blood --yes
sudo pz story scan-status story_test
sudo pz story scan-report story_test --output /var/tmp/smokeys-fresh-v3.json
python3 story/campaign/smokeys_dressing_plan.py \
  --scan /var/tmp/smokeys-fresh-v3.json \
  --output /var/tmp/smokeys-dressing-preview.json
```

Планировщик выводит отдельные **dry-run** команды, отбирает только
`smokeys_bar_*` Story item-токены в границах здания и только реальные
`table_surface=true`, не более 3 предметов на поверхность.
Ориентировочная высота 0.65 подлежит игровой калибровке.
Не использовать старый скан: он предшествует текущему луту из видео.

## 4. ВСЕ окна Smokey's

Исходный owner-скан от 2026-10-17 содержал **17 `IsoWindow` на Z=0 и
15 на Z=1**, всего 32 окна в периметре X10615–10628,Y9212–9235.
Ранее `smokeys_bar_06_fortification` обрабатывала лишь 3 окна.

Новый read-only `smokeys_window_plan.py` требует свежего полного v3
`--include windows,squares` и проверяет **каждый из исходных 32
индекс/спрайт/координат**:

- если окно уже забаррикадировано — не трогаем;
- если стекло уже разбито, но досок нет — **заколачиваем его всё равно**;
- каждое окно без баррикады получает `barricade` (1–4 доски),
  в баре **не** предусмотрено специального разбивания стекол;
- если окно открыто, целевая клетка не загружена, индекс/спрайт изменён
  или скан не знает состояния — **STOP**, разбор вручную.

```bash
python3 story/campaign/smokeys_window_plan.py \
  --scan /var/tmp/smokeys-fresh-v3.json \
  --output /var/tmp/smokeys-32-windows-preview.json
```

Он **не применяет ничего**; печатает только команды с
`--type barricade --planks 1..4 --allow-barricades`, без `--yes`.
Codex применяет **одну** операцию, ждёт `live-status`, проверяет
через скан её результат, затем продолжает.
Если исходное окно исчезло из мира, план не заявит ложный PASS.

## 5. Однократная очистка загруженных зомби в радиусе 10 клеток от бара

Отдельная серверная команда охватывает расстояние **до 10 клеток от
всего контура** X10615..10628,Y9212..9235, уровни Z0..1. Использует
`IsoCell.getZombieList()`, проверяет несколько известных загруженных
клеток, а для удаления вызывает `VirtualZombieManager.instance:
removeZombieFromWorld`. Никакой `road_home` или соседних домов.

```bash
sudo pz story bar-zombies inspect story_test --yes
sudo pz story bar-zombies-status story_test

# Число N берётся ТОЛЬКО из успешного server inspection:
sudo pz story bar-zombies clear story_test --expect N --yes
sudo pz story bar-zombies-status story_test
```

Предохранители: число не более 256, точное совпадение `--expect`
с текущим счётом, все игроки должны отойти минимум на 12 клеток от
границ зоны; контрольная запись до первой мутации, прежний запрос
не повторяется после рестарта. Очищаются только **активные загруженные
`IsoZombie` внутри периметра и в десяти клетках от стен**; незагруженные
участки не выдаются за очищенные. Никакого глобального удаления зомби,
трупов, предметов или принудительного спавна.

Это **однократная зачистка**: миграция с улицы и последующие обычные
спавны не запрещены. Если нужно держать бар всегда свободным от
заражённых, требуется отдельно согласовать правила зоны и оценить
периодическую CPU-нагрузку. Сейчас непрерывной зачистки нет.

### Приёмка и эксплуатация

- PR и GitHub CI ≠ проверка на реальном MP. Требуются pinned B42.21
  Kahlua/JVM acceptance и затем два клиента.
- Для новых Lua mount нужен согласованный краткий рестарт
  **только игрового контейнера** с root-approved cold backup, RCON
  `players=0`, без сброса или восстановления `story_test`.
- Сначала read-only скан и одна безопасная пробная вещь на столе.
  Затем перенос одного помеченного предмета и перезапуск/двухклиентная
  проверка. Только после этого остальной реквизит.
- Зомби сначала inspect, затем clear с точным количеством. Не применять
  очистку при присутствии людей внутри бара.
- Окна — сначала один тестовый window/barricade и осмотр обоими клиентами,
  затем остальные с подтверждением каждой операции.
- Итог: сохранённые объекты, отсутствие дубликатов и точная проверка
  каждого из 32 окон. `road_home` не трогать.
